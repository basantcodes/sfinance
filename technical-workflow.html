Finance Journal
Technical Workflow Review

Project Structure & Technical Workflow

This Android app is a personal finance management system with account tracking, transactions, budgets, loans, wishlist planning, journal notes, dashboard analytics, and export support. It is built around Jetpack Compose, Room persistence, ViewModel-driven UI state, and a repository layer for business logic.

1. System Architecture Overview

1

UI Layer

Compose screens and dialogs in the app package. Main navigation, modals, record forms, dashboard cards, and transaction flows live here.
2

ViewModel

FinanceViewModel holds auth state, filter state, dashboard state, and live application data updates.
3

Repository

FinanceRepository contains business rules like validation, account balance checks, affordability logic, dashboard computing, and data mutation methods.
4

Local Data

Room database and entity models store users, accounts, categories, transactions, budgets, journals, loans, and wishlist items.
5

Secure layer

Authentication uses BCrypt password hashing and JWT-based token persistence in preferences.

3. Actual Workflow in the App

  • App launch: MainActivity starts, enables edge-to-edge mode, loads auth state and UI event flow.
  • Authentication: On startup, FinanceViewModel checks the active user. If not present, it creates a demo user and logs them in automatically.
  • Data hydration: On user login, refreshAllData starts several collectors for accounts, categories, budgets, transactions, loans, journal, and wishlist.
  • Dashboard refresh: Repository computes dashboard metrics based on current month/year and user data.
  • Transactions: user actions add/edit/delete transactions; repository validates account balances before mutating state.
  • Budget & wishlist: repository calculates spending coverage, affordability thresholds, and progress percentages.
  • Export: PDF exporter can generate reports from dashboard and transaction data.

4. What Is Strong in the Current Design

Good: Clear separation between UI state, repository logic, and local persistence.
Good: Room entities are structured around the real domain model and indexed for common access patterns.
Good: Security basics are in place: password hashing with BCrypt and token-based session tracking.
Good: Dashboard data and budget logic are aggregated centrally, reducing duplication across screens.
Good: Compose UI allows fast iteration and coherent user experience in a single app shell.

5. Weaknesses & Technical Debt

Area Issue Impact Priority
App shell / UI composition MainActivity and MainAppScaffold are overloaded with navigation, dialog state, screen logic, and event handling. Hard to maintain, harder to scale, increasing regression risk. High
ViewModel responsibilities FinanceViewModel owns auth, dashboard, account, budgets, loans, wishlist, journal, PDF-related actions, and data refresh orchestration. Single giant state container; not aligned with feature-by-feature boundaries. High
Repository boundary leakage ViewModel directly accesses database DAO and refreshes some state outside repository patterns. Tight coupling; logic is spread across layers instead of being centralized. High
Database migration strategy Room database uses fallbackToDestructiveMigration() and version 1 only. Unsafe for user data over longer-term app growth and versioned releases. High
Authentication behavior Auto-create demo user, auto-rename user names, and hardcoded values in auth boot flow. Magic behavior; not configurable and may confuse real users and production onboarding. Medium
State flow duplication Multiple collectors triggering refreshDashboard and refreshWishlist repeatedly. Performance overhead and harder reasoning when UI state updates race each other. Medium
Testing coverage Most critical flows appear to be business logic and data mutation features without deep automated tests. Risk of silent regressions in core financial logic. High
Dependency management No DI framework such as Hilt or Koin. Manual dependency wiring makes the app harder to scale and harder to test. Medium
Domain clarity String-based enums and raw IDs are common; some validation is not strongly typed. Prone to invalid state and more runtime bugs. Medium
Security production posture Token storage in preferences is convenient but not the strongest production setup. Requires stricter token lifecycle and encrypted storage for real-world deployments. Medium

6. Specific Improvement Recommendations

Phase 1: Stabilize
  • Introduce explicit feature-level ViewModels per screen or module.
  • Separate navigation and modal state from MainActivity.
  • Add migration handling and schema versioning in Room.
Phase 2: Refactor architecture
  • Use Hilt for dependency injection and better lifecycle management.
  • Move data-init and heavy aggregation logic into dedicated use cases or services.
  • Use sealed UI states for each screen instead of ad hoc mutable state flags.
Phase 3: Quality & resilience
  • Add repository and transaction tests: balances, budget math, loans, affordability rules.
  • Introduce robust error handling and user-friendly validation messages.
  • Track analytics and crash reporting for business-critical flows.
Phase 4: Product maturity
  • Support cloud sync and multi-device backup.
  • Add export/import, encrypted backups, and stronger auth lifecycle controls.
  • Improve dashboard customization, filtering, and reporting depth.

8. Bottom Line

This is a functional and feature-rich personal finance app with a solid MVP foundation. The main issues are not a lack of ideas or capability, but architectural scale and maintainability as the product grows. The next step is to split the monolithic screen logic, enforce cleaner boundaries between layers, and build automated testing around the finance rules.
